# Техническое задание: OSS Bot (MVP)

> Примечание: документ исторический — это ТЗ исходного MVP (проект ранее
> назывался Student Bot). Актуальная документация: [README.md](README.md),
> [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md), [docs/WEB_ADMIN_GUIDE.md](docs/WEB_ADMIN_GUIDE.md).

## 1. Цель и границы проекта
Создать минимально жизнеспособный продукт (MVP) для приёма и маршрутизации обращений студентов через VK с управлением через защищённую веб-панель. 
**Границы MVP:** 
- Только VK как клиентский канал.
- Только веб-панель для администраторов (без мобильных приложений).
- **Отказ от внешней отчётности:** email-рассылок. Вся аналитика доступна как в отчете, так и внутри веб-панели.
- Приоритет: стабильность ядра, надёжная доставка сообщений (Outbox) и безопасность данных.

## 2. Архитектура и компоненты
Система состоит из 4 изолированных слоёв:
1. **Bot Layer (`bots/vk`)**: Асинхронный VK-бот на `vkbottle`, отвечающий только за взаимодействие с пользователем и сбор данных через FSM (Finite State Machine).
2. **Core Layer (`core`)**: Бизнес-логика, работа с БД (SQLAlchemy), паттерн Outbox для гарантированной доставки ответов из веб-панели в VK, валидация конфигурации.
3. **Web Layer (`web`)**: Административная панель на FastAPI + Jinja2. Серверный рендеринг для скорости разработки.
4. **Data Layer**: PostgreSQL + Alembic для управления миграциями схемы.

## 3. Роли и права доступа
- **Студент**: Инициатор заявки. Может создать обращение, просмотреть историю и статус своих заявок.
- **Администратор отдела**: Видит и обрабатывает заявки только своего отдела. Может менять статус, отвечать, просматривать историю.
- **Суперадмин**: Полный доступ. Управление администраторами, просмотр всех заявок и логов действий, базовая внутренняя аналитика (количество заявок по статусам).

## 4. Минимальная схема базы данных
- `users`: `id`, `vk_id`, `full_name`, `dormitory`, `created_at`
- `departments`: `id`, `name` (Жилбыт, Культмасс, Информ, Корпоративный)
- `admins`: `id`, `user_id` (vk_id), `department_id`, `role` (ADMIN, SUPERADMIN)
- `tickets`: `id`, `user_id` (nullable для анонимных), `department_id`, `topic`, `description`, `status`, `response_text`, `is_anonymous`, `created_at`, `updated_at`
- `outbox_messages`: `id`, `ticket_id`, `payload`, `status` (pending, sent, failed), `attempts`, `created_at`
- `logs`: `id`, `admin_id`, `action`, `details`, `created_at`

## 5. Критерии готовности MVP
1. Студент проходит сценарий создания заявки, данные сохраняются в БД.
2. Администратор видит заявку в веб-панели, может изменить статус и написать ответ.
3. Ответ администратора гарантированно доставляется студенту в VK (через Outbox).
4. Веб-панель доступна только через Tailscale с принудительной авторизацией и HTTPS.
5. Код покрыт линтерами (ruff, mypy) и базовыми интеграционными тестами (pytest).
6. **Параллельные сессии**: Несколько администраторов могут работать одновременно с разных аккаунтов/браузеров без взаимного влияния.

## 6.1. Параллельные сессии и отказоустойчивость (Реализовано)

### Цель
Обеспечить одновременную работу нескольких администраторов с разных аккаунтов/браузеров без взаимного влияния.

### Архитектура
- **SessionMiddleware**: RedisSessionMiddleware с подписанными cookie (`secret_key` из `.env`)
- **Хранение сессий**: Распределённое хранилище Redis с настраиваемым TTL (`SESSION_TTL`)
- **CSRF-защита**: CSRFMiddleware — токен хранится в сессии, проверяется на все POST-запросы (внешние вебхуки Callback API исключены)
- **Rate limiting**: БД-хранилище (`login_attempts`) — 5 неудачных попыток за 15 минут на IP

### Порядок выполнения middleware
```
SecurityHeaders → Session → CSRF → CORS → handler
```

### Безопасность
- CSRF-защита для всех POST-запросов
- Rate limiting: 5 неудачных попыток за 15 минут на IP (хранилище — PostgreSQL)
- Security headers: X-Frame-Options, CSP, X-Content-Type-Options

### Тесты
- `tests/test_parallel_sessions.py`: тесты для проверки:
  - Входа администратора (bootstrap и web_users)
  - Изоляции сессий
  - Выхода из системы
  - Заголовков безопасности
  - Rate limiting

### Масштабирование
При переходе на несколько uvicorn-workers необходимо:
1. Ограничить `WEB_WORKERS=1` (без Redis сессии многопроцессность небезопасна)
2. Либо заменить cookie-сессию на Redis-backed SessionMiddleware

## 6.2. Многопроцессный rate limiting (Реализовано)

### Проблема
In-memory `RateLimiter` (словарь `requests: dict[str, list[float]]`) хранил состояние
в памяти каждого процесса Python. При `--workers 4` каждый воркер имел свой лимит,
что учетверяло доступные запросы и позволяло обходить защиту.

### Решение
- **DBRateLimiter** (`web/security/middleware.py`): использует таблицу `crud_attempts`
  для хранения состояния. Работает корректно при любом количестве воркеров.
- **Таблица `crud_attempts`**: создаётся миграцией `e8f9a0b1c2d3`, индексы по `(ip, action, attempted_at)`.
- **Применение**: CRUD-операции админ-панели (смена статуса, ответы, создание заявок)
  используют `DBRateLimiter` с лимитом 20 операций на IP за 5 минут.
- **Login attempts**: уже использовали БД (`login_attempts`) — доработок не требуется.

## 6.3. Асинхронный SMTP (Реализовано)

### Проблема
`send_report_email` использовал синхронный `smtplib.SMTP` через `asyncio.to_thread`.
Хотя вызов не блокирует event loop полностью, использование синхронных сокетов
внутри асинхронного цикла — технический компромисс.

### Решение
- Заменён на `aiosmtplib.send()` — полностью асинхронная отправка.
- Убрана зависимость `smtplib`, добавлена `aiosmtplib==4.0.0`.
- Вызов `send_report_email` в `_run_report` больше не требует `asyncio.to_thread`.

## 7. Логика работы отделов (Реализуется в последнюю очередь)
*Данный блок реализуется строго после утверждения и тестирования ядра (БД, Outbox, базовая авторизация, создание тикета).*

### 7.1. Жилбыт
- **Сценарий**: Пошаговый сбор данных через FSM (ФИО → Общежитие → Тема → Описание).
- **Оптимизация**: Перед созданием тикета текст описания проверяется по простой таблице `knowledge_base` (ключевые слова). При совпадении тикет создаётся сразу со статусом `Выполнено (авто)` и ответом из БЗ.
- **Статусы**: `Новое` → `В обработке` → `Передано в Хозчасть` → `Выполнено`.

### 7.2. Культмасс
- **Сценарий**: Упрощённая анкета (ФИО → Тема → Описание). 
- **Фича**: Возможность массового ответа (рассылки) по списку отфильтрованных тикетов из веб-панели (например, "Всем, кто спрашивал про Новый год").

### 7.3. Информ
- **Сценарий**: Интерактивное FAQ-дерево. Студент выбирает варианты ответов через inline-клавиатуры VK, не создавая тикет.
- **Эскалация**: На любом шаге доступна кнопка «Связаться с администратором», которая прерывает дерево и создаёт тикет в отдел "Информ" с историей выбранных пунктов.

### 7.4. Корпоративный
- **Сценарий**: Максимально упрощённый поток. Сбор ФИО, общежития, темы и описания в 4 шага.
- **Особенность**: Нет автоответов и сложных статусных цепочек. Только `Новое` → `В обработке` → `Закрыто`.

### 7.5. Анонимное обращение (Опционально)
- **Сценарий**: Запрос только текста обращения.
- **Хранение**: `user_id = NULL`, `department_id = NULL`, статус `Анонимное`. Доступно для просмотра только роли `SUPERADMIN`.

## 8. Развитие системы: от MVP к релизу v0.7.8 (Enterprise Grade)

В версии v0.7.8 проект полностью вышел из стадии базового MVP и получил корпоративную архитектуру:

### 8.1. Распределённые сессии и многоворкерный режим
- Интегрирован сервис `oss_bot_redis` (`redis:7-alpine`).
- Реализован `RedisSessionMiddleware` (`web/security/session_store.py`) с бесшовным fallback на in-memory хранилище при локальной разработке.
- Веб-панель масштабируется на любое количество воркеров (`WEB_WORKERS=2+`) без риска потери сессий и рассинхронизации CSRF-токенов.
- Доставка фоновых сообщений координируется распределёнными блокировками `pg_try_advisory_lock` в PostgreSQL (`core/task_dispatcher.py`).

### 8.2. Двухфакторная аутентификация (2FA через VK)
- Реализован надёжный двухфакторный вход для операторов панели: генерация криптостойкого 6-значного OTP-кода и мгновенная отправка в личные сообщения администратора через Outbox-очередь бота.
- Защита bootstrap-входа: автоматическая блокировка учетных данных из `.env` при регистрации постоянного суперадмина и визуальный баннер-предупреждение при временной bootstrap-сессии.

### 8.3. Распределённый кэш с TTL и инвалидацией
- Внедрён модуль `core/cache.py` для кэширования ресурсоёмких запросов (отделы, ключевые слова, FAQ, дашборд) с настраиваемым TTL (`CACHE_DEFAULT_TTL=300`).
- Поддерживается wildcard-инвалидация ключей по маске при любых операциях создания/редактирования/удаления данных.

### 8.4. Версионированный REST API v1
- Выделен роут `/api/v1/` с полной валидацией входных и выходных DTO через схемы Pydantic v2 (`web/schemas.py`).
- Интерактивная документация Swagger UI (`/docs`) и ReDoc (`/redoc`).

### 8.5. Наблюдаемость: Prometheus и Sentry SDK
- Реализован эндпоинт метрик Prometheus (`/metrics`) для сбора статистики запросов, задержек и системных событий.
- Централизованный сбор исключений через Sentry SDK (`core/sentry.py`, `core/bot_core.py`, `web/main.py`).

### 8.6. Редизайн веб-панели и UX
- Дизайн-система Dark Graphite + Neon Pink (`#ff4d9d`).
- Моментальный живой поиск по таблицам на стороне клиента, интерактивные фильтры по статусам с динамическими счётчиками, модальные окна для детального просмотра и ответов на обращения.
- Устранена проблема N+1 запросов при сопоставлении ключевых слов отделов за счёт пакетной загрузки в память.

### 8.7. Дружелюбная обработка ошибок
- Пользователям и администраторам выводится понятная рекомендация: *"Произошла ошибка. Пожалуйста, сфотографируйте экран и отправьте техническому администратору"* вместе с уникальным `error_id` для мгновенной локализации в логах и Sentry.
