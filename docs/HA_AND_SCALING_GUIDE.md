## 1. Пулинг соединений: PgBouncer

### Зачем нужен PgBouncer
Каждый рабочий процесс Uvicorn, фоновый воркер бота и задача Outbox создают пул асинхронных соединений `asyncpg`. Без пулера при увеличении числа воркеров база данных PostgreSQL быстро исчерпает лимит `max_connections` (вызывая ошибку `FATAL: too many connections`).

PgBouncer включён в стек в режиме **транзакционного пулинга** (`pool_mode = transaction`, порт `6432`):
- Клиентские подключения удерживают физическое соединение к СУБД только на время исполнения конкретной транзакции.
- Сотни одновременных веб-запросов обслуживаются компактным пулом из 15–20 реальных соединений к PostgreSQL.

### Требования к совместимости:
1. **Отключение кэша выражений**: в `core/database.py` установлен параметр `statement_cache_size = 0`, так как при смене серверного соединения в режиме транзакций подготовленные выражения `asyncpg` сбрасываются.
2. **Миграции через прямой порт 5432**: команды DDL (Alembic) выполняются через контейнер `migrate` напрямую к порту 5432, не затрагивая пул PgBouncer.
3. **Блокировки без `advisory_lock`**: периодические фоновые задачи используют распределённые замки в Redis (`core/task_dispatcher.py`), так как блокировки уровня сессии не совместимы с транзакционным пулингом.

## 2. Режимы работы бота: Callback API vs Long Poll

| Параметр | Long Poll (`VK_MODE=longpoll`) | Callback API (`VK_MODE=callback`) |
|---|---|---|
| **Принцип работы** | Бот сам опрашивает серверы VK по HTTP | Серверы VK присылают входящие POST-запросы (вебхуки) |
| **Публичный IP/домен** | Не требуется | Обязателен белый IP и HTTPS (Caddy) |
| **Масштабирование** | Строго 1 процесс бота (иначе дублируются события) | Любое число процессов за балансировщиком |
| **Рекомендация** | Локальная разработка и тест | **Production с высокой нагрузкой** |

### Как включить Callback API в продакшене:
1. В настройках сообщества ВК перейдите в **Управление** → **Работа с API** → **Callback API**.
2. Укажите адрес сервера: `https://<ваш_домен>/api/v1/vk/callback`.
3. Скопируйте строку подтверждения и секретный ключ в файл `.env`:
   ```env
   VK_MODE=callback
   VK_CONFIRMATION_TOKEN=ваша_строка_подтверждения
   VK_CALLBACK_SECRET=произвольный_длинный_секретный_ключ
   ```
4. Нажмите в ВК кнопку «Подтвердить».
5. Во вкладке «Типы событий» отметьте: *Входящие сообщения*, *Редактирование сообщений*.

## 3. Мультиворкерный режим и распределённое состояние в Redis

Для полноценного использования всех ядер процессора веб-сервер запускается с несколькими воркерами:
```env
WEB_WORKERS=4
```

Благодаря выносу состояния в **Redis 7**:
- **Сессии пользователей**: администратор может отправлять запросы на любые воркеры без разрыва сессии (`RedisSessionMiddleware`).
- **Защита от брутфорса**: счётчик попыток входа (`DBRateLimiter`) синхронизирован между всеми процессами.
- **Одноразовые пароли 2FA**: проверяются атомарно независимо от воркера.
- **Outbox Worker**: распределённый замок (`SET NX PX`) исключает отправку одного и того же ответа двумя параллельными процессами.

## 4. Нагрузочное тестирование с Locust

Для проверки поведения системы под нагрузкой используется скрипт `tests/load/locustfile.py`.

### Запуск теста в терминале:
```bash
# Тест с 50 параллельными пользователями, приток 10 пользователей в секунду
locust -f tests/load/locustfile.py --headless -u 50 -r 10 -t 1m --host http://localhost:8000
```

### Запуск с интерактивным Web UI:
```bash
locust -f tests/load/locustfile.py --host http://localhost:8000
```
Откройте в браузере `http://localhost:8089` для наблюдения за графиками RPS, процентилями задержек (p50, p95, p99) и статусами ответов.

## 5. Метрики и мониторинг (Prometheus)

Метрики собираются на эндпоинте:
```
GET /metrics
```

### Ключевые показатели для мониторинга:
1. **Задержка ответа (p95 latency)**: норма < 200 мс. Алерт при > 1.0 с.
2. **Процент ошибок HTTP 5xx**: норма < 0.1%. Алерт при > 2% за 5 минут.
3. **Размер очереди Outbox**: количество неотправленных сообщений. Алерт при накоплении > 50 сообщений.
4. **Heartbeat бота**: контейнер бота регулярно обновляет контрольный файл. При отсутствии обновлений более 3 минут бот считается зависшим.
5. **Использование памяти Redis**: алерт при заполнении свыше 85%.

## 6. Отказоустойчивость: Репликация PostgreSQL и Redis Sentinel

При развёртывании в High-Availability (HA) кластере:
1. **PostgreSQL Streaming Replication**:
   - Master-сервер ведёт запись (WAL) и передаёт изменения на Standby-сервер в режиме реального времени.
   - При аппаратном сбое основного сервера трафик переключается на Standby без потери истории тикетов.
2. **Redis Sentinel**:
   - Кластер из 3 узлов Sentinel следит за состоянием мастера Redis.
   - При отказе мастера за доли секунды происходит автоматический failover и выбор нового лидера.
