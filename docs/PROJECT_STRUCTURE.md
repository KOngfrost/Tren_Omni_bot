# Структура проекта OSS Bot

Документ описывает, где что лежит и почему выбрана именно такая раскладка.
Актуален для релиза **0.8.6** (этап 5 — аудит безопасности, WAF, стабильность кнопок, автотесты).

---

## 1. Общая схема

```
student_bot/
├── core/                  # Доменное ядро: бизнес-логика, общая для всех сервисов
├── bots/                  # Боты для мессенджеров (клиенты доменного ядра)
├── web/                   # Веб-панель администратора (FastAPI)
├── backend_go/            # Высоконагруженный Go-шлюз (Fiber)
├── alembic/               # Миграции схемы БД
├── tests/                 # Автотесты (pytest + Playwright)
├── scripts/               # Утилиты обслуживания (бэкапы, хеши, генерация конфигов)
├── monitoring/            # Мониторинг (Prometheus, правила алертов)
├── pgbouncer/             # Конфигурация пула соединений PostgreSQL
├── docs/                  # Проектная и эксплуатационная документация
├── alembic.ini            # Конфигурация Alembic
├── docker-compose.yml     # Оркестрация всего стека
├── Caddyfile              # TLS и reverse-proxy
├── Dockerfile             # Образ бота (основной сервис)
├── Dockerfile.web         # Образ веб-панели
├── Dockerfile.monitor     # Образ Telegram-бота мониторинга
├── pyproject.toml         # Линтер (ruff), тесты (pytest), покрытие
├── mypy.ini               # Статическая типизация
└── requirements*.txt      # Зависимости (основные / для разработки)
```

## 2. Почему именно такая структура

Проект — **монолит с чётким внутренним разделением по слоям**, а не микросервисы.

| Решение | Причина |
|---|---|
| `core/` отдельно от `bots/` и `web/` | Бизнес-логика заявок, outbox и отчётов не должна дублироваться между VK-ботом, Telegram-ботом и веб-панелью. Сейчас её используют все три. |
| `bots/<мессенджер>/` | Адаптеры под конкретный API (vkbottle, aiogram) изолированы. Добавление нового мессенджера не затрагивает `core/`. |
| `web/` отдельно от `core/` | Панель запускается отдельным процессом с `WEB_WORKERS`. Объединение с ботом означало бы общий event loop и общие простои. |
| `backend_go/` отдельным языком | Осознанное исключение: Go-шлюз нужен там, где Python не справляется по пинговой задержке. Он обращается к той же БД и Redis, но не импортирует Python-код. |
| `pgbouncer/` и `monitoring/` рядом с compose | Конфигурация инфраструктуры версионируется вместе с кодом: рост числа воркеров без правки пула соединений приводит к исчерпанию `max_connections`. |

### Чего в структуре сознательно нет

* **`src/`** — прототип не является устанавливаемым пакетом; запускается как
  сервис из корня. Псевдо-изоляция в `src/` дала бы только лишний уровень
  вложенности при нулевом выигрыше.
* **`packages/`, `apps/`** — терминология из JS-экосистем. В Python-проекте
  аналогичную роль играют `core/` (переиспользуемое) и `bots/`, `web/`,
  `backend_go/` (приложения).
* **`libs/`, `common/`** — «свалка общих утилит» — антипаттерн: непонятно,
  кому принадлежит код. Общие механизмы живут в `core/` по смыслу
  (см. `core/ticket_service.py`, `core/outbox.py`).

## 3. Слои и правило зависимостей

Зависимости идут **строго в одну сторону**:

```
  bots/  ─┐
          ├─→  core/  ─→  БД (SQLAlchemy) / Redis
  web/   ─┘
  backend_go/  ──→  БД (pgx) / Redis          (напрямую, без core/)
```

1. **`core/` не импортирует ничего из `bots/`, `web/`, `backend_go/`.**
   Нарушение означает, что бизнес-логика «знает» о представлении — признак
   неверно выбранного слоя.
2. **`bots/` и `web/` могут импортировать `core/`, но не друг друга.**
   Иначе бот и панель связаны напрямую.
3. **`backend_go/` изолирован.** Общего Python-кода с ним нет; общая
   контракта держится на уровне схемы БД и HTTP API.

### Проверка на практике

```bash
# В core/ не должно быть ни одного импорта из web/ или bots/
grep -rnE "^from (web|bots)\.|^import (web|bots)\." core/
```

## 4. Инфраструктурные каталоги (этап 5)

### `pgbouncer/` — конфигурация пула соединений (SEC-12)

* `pgbouncer.ini` — конфигурация с прозрачной авторизацией через
  PostgreSQL (`auth_query`). Смонтирована в контейнер в режиме `:ro`,
  поэтому автогенерация образа не выполняется и **все параметры
  обязательны явно**.
* `userlist.txt` — генерируется сервисом `pgbouncer-userlist` при старте
  стека, в Git **не хранится** (см. `.gitignore`). Содержит только
  SCRAM-SHA-256 verifier служебной роли, а не пароль.

Функция `pgbouncer.get_auth(TEXT)` создаётся миграцией Alembic
`b4c5d6e7f8a`. Она отдаёт PgBouncer верификатор любого пользователя
из `pg_authid`, поэтому держать в `userlist.txt` пароли всех клиентов БД
не требуется.

### `monitoring/prometheus/`

* `prometheus.yml` — сбор метрик. Две задачи: `oss_bot_web` (веб-панель)
  и `oss_bot_go_api` (Go-шлюз).
* `alerts.yml` — правила алертов. Метрики Go-сервиса имеют префикс
  `oss_bot_go_api_` и не смешиваются с метриками FastAPI, поэтому
  алерты не срабатывают на смешанных запросах.

### Healthcheck-контуры

| Сервис | Проба | Смысл |
|---|---|---|
| `db` | `pg_isready` | Сервер БД принимает подключения. |
| `redis` | `redis-cli ping` | Кэш и сессии доступны. |
| `pgbouncer` | `psql` через сам пул | Проверяется не только порт, но и SCRAM-аутентификация и работа `auth_query`. |
| `web-admin` | `HTTP GET /health` | БД доступна, время синхронизировано. |
| `go-api` | `wget` к `/api/v1/health` | Живой TCP+HTTP: ловит и падение процесса, и зависание event loop. |
| `bot` | `scripts/healthcheck_bot.py` | Свежесть heartbeat-файла (бот обрабатывает события). |

## 5. Тесты

```
tests/
├── conftest.py                  # Фикстуры: in-memory SQLite, TestClient
├── test_ui_buttons_browser.py   # E2E: реальный Chromium, CSP включён (этап 5.4)
├── test_all_web_buttons.py      # HTTP-уровень: все кнопки панели
├── test_all_telegram_buttons.py # Кнопки Telegram-бота
├── test_csp_nonce.py            # Регрессия: nonce в CSP совпадает со скриптами
└── load/locustfile.py           # Нагрузочное тестирование
```

Правило: **для проверки «кнопка нажимается» используется браузер**, для
проверки «обработчик отвечает верно» — HTTP-клиент. Браузерные тесты
пропускаются (`skipif`), если Playwright не установлен: в CI образ без
браузера допустим.

Go-тесты живут рядом с кодом в `backend_go/internal/handlers/` и
запускаются отдельно: `cd backend_go && go test ./...`.

## 6. Правила добавления кода

1. **Новая бизнес-логика → `core/`.** Если она нужна двум и более
   сервисам, она не должна дублироваться.
2. **Новый мессенджер → `bots/<name>/`,** с обёртками над `core/`.
3. **Новый эндпоинт панели → `web/routes/`,** бизнес-логика — в `core/`.
4. **Новая метрика** регистрируется в `internal/metrics` (Go) или через
   `prometheus_client` (Python) и сразу описывается алертом, если она
   отражает отказ.
5. **Новая миграция обязана оставлять ровно одну голову** (`alembic heads`
   возвращает один идентификатор). Это проверяется в CI.
6. **Комментарии и docstring — на русском,** как принято в проекте.
